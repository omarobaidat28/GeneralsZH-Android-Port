## 2026-11-09: On-screen buttons editor in the launcher (not compiled yet)

Third part of the launcher work below. Reading the engine first changed the job: the overlay the
owner asked for on 21/10 is already whole in `SDL3GameEngine.cpp` (`gxvirtualkeys`: up to 16
buttons from `gx_virtual_keys.ini`, each pressing a key through `GxVirtualKeysSendKey`, hidden
while a keyboard or mouse is attached). What was missing is the other end of its contract --
nothing in the launcher ever wrote that file, so the overlay could only be reached by composing
the INI by hand. No input code was touched; the overlay keeps consuming fingers in the SDL pump
and pushing key events, as before.

**Launcher.** `ControlsLayouts.java` keeps named layouts as JSON in the launcher's preferences
and writes the selected one into the folder of the game about to start
(`GeneralsZHActivity.onCreate()`, both games, the legacy `GameData` folder included).
`ControlsEditorActivity.java` is the editor: a frame with the proportions of the phone's screen,
buttons drawn where the game will draw them; drag to move, tap to change key, label, held
modifiers and size, or delete. Opacity, overall size and the auto-hide switch per layout; new /
rename / delete for layouts. Every change is stored at once. Interface tab: a card with the
switch, the layout's name and button count, and the entry to the editor. The first use makes a
starting layout (1-5 and Ctrl on the left edge, Q W E R and Shift on the right).

A file in the game folder that the launcher did not write is renamed to `.bak` before the first
write, not overwritten; and nothing is written at all for a player who never opened the feature.
Numbers go out with `Locale.ROOT` -- the engine reads them with `atof()`, and an Arabic or Farsi
phone would otherwise write digits it cannot parse.

**Engine (`Core/`, so both games).** Three defects in the overlay's parser that the editor would
have run into, and one addition:
- `ButtonDef` had no defaults, and the parser's first one was default-initialized: its scancode
  was stack garbage, so the "is there a button to flush" test could emit a button nobody defined.
- `key=LSHIFT` / `LCTRL` / `LALT` / `KP_ENTER`, the names the file's own header documents, are not
  names `SDL_GetScancodeFromName` knows (SDL's contain a space, and a value ends at the first
  space), so a modifier defined as a button was dropped. Now an alias table in front of SDL's.
- `mods=lalt` and `mods=ralt` both set `SDL_KMOD_ALT`; the press code sends Right Alt whenever
  that bit is set, so "lalt" pressed Right Alt. Each side now sets its own bit.
- New `size=` per button (0.5..2.5 of the layout's unit), for placed buttons.

**Texts.** 17 new strings in all 13 locales.

**Not verified.** As below: no JDK, Gradle or NDK on this machine, so neither the Java nor the
C++ has been compiled, and nothing has run on a device. To check on a phone: the starting layout
appears in game where the editor shows it; Ctrl held + 1 makes a group and 1 selects it; a dragged
button lands in the same place in game; the buttons hide with a keyboard attached; an Arabic-locale
phone writes an INI the engine reads. The editor's label size is an estimate of the engine's.

## 2026-11-09: Launch profiles and a launcher-style Home (not compiled yet)

Owner's ask: make the launcher work like PojavLauncher does for Minecraft. The launcher already
had most of what that means (game folder, two games, mods, renderer, custom driver, account, logs,
updates); what it lacked was the thing a Pojav user touches first -- a named profile picked above
Play. Scope agreed with the owner in four parts: profiles, a launcher-style Home, an on-screen
controls editor, a standalone launcher app. This entry covers the first two.

**Profiles (`LaunchProfiles.java`).** A profile is a named set of what decides the next start:
the game, that game's mod list (order and switches), the simulation rate, the renderer and the
intro switch. The design choice that keeps it small: the launcher's settings stay where they were
(preferences and the marker files the engine reads) and they *are* the selected profile. The
stored copy of the selected profile is refreshed from those settings each time the list is loaded,
and picking another profile writes its values into the same settings. No reader of a setting --
`GeneralsZHActivity`, `ModManager.writeActiveList`, `GeneralsOnlineSession` -- had to learn about
profiles, and a setter anywhere (the Mods screen, Graphics, GeneralsOnline moving the rate to
60 Hz) changes the selected profile without calling into the new class. An install with no
profiles gets one made of its current settings, so nothing changes until a second is added.
Stored as JSON in the launcher's preferences (`launch_profiles`, `launch_profile_active`).

Shared by all profiles on purpose: game folders, interface and language settings, and what lives
in each game's `Options.ini` (upscaler, text size, interface scale).

Two guards: a profile saved with the experimental Vulkan renderer falls back to OpenGL ES when
that switch is off (it must not reintroduce a hidden choice), and selecting a Vulkan profile runs
`applyRecommendedDriverIfNeeded()` as the Graphics page would have.

**Home.** Order is now account, profile + Play, then the cards the profile is made of (Game,
Game Folder), then Updates. The GeneralsOnline card became one row at the top (name, who is
signed in, tap to open). Play moved from between two cards into the profile card, under the row
that says what it will start ("Zero Hour · Mods on: 2 · 60 Hz · GLES"). The Simulation Rate and
Render Backend cards each carry a chip naming the profile they are kept in.

**Texts.** 12 new strings in all 13 locales; `setup_game_desc` lost its second sentence
("Graphics and interface options apply to both") in all 13, since the rate and the renderer now
follow the profile. Help texts that point at Home controls by position were checked and still
hold (the Game card is still above the folder card).

**Not verified.** Written on a machine with no JDK, Gradle or NDK: the Java has not been compiled
and nothing has run on a device. Needs a local build and a pass over: first start (one "Default"
profile, same settings as before), new / rename / delete, switching between a Zero Hour and a
Generals profile, and a profile with mods against one without.

**Next.** The controls editor (entry above), then the question of a standalone launcher app.
